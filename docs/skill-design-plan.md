# 한국어 대화형 프롬프트 스킬 설계 계획

2026년 10월 9일 작성. 같은 날 초기 구현과 사용자 전역 설치를 완료했다. [스킬 원본](../skills/korean-prompt-dialogue/SKILL.md)과 [검증 기록](skill-validation.md)을 참고한다. 아래 비교 실험 계획은 아직 수행하지 않았으며, 이번 확인은 구조 검증과 소규모 행동 점검이다.

한국어로 편하게 말한 아이디어나 수정 요청을 대화로 구체화하고, 사용자가 원하는 결과와 조건을 보존한 실행용 프롬프트로 만드는 스킬을 제안한다. 성공 기준은 프롬프트의 길이나 전문적인 표현이 아니라 **의도 보존, 결과의 적합성, 대화에 드는 부담**이다.

언어학적 근거와 적용 한계는 [한국어와 대화 연구](korean-language-research.md), 자료별 확인 범위는 [출처와 근거](sources.md)에 정리한다. 이 문서의 동작 규칙과 평가 수치는 앞으로 검증할 설계안이다.

## 사용자가 해결하려는 문제

사용자는 처음부터 완성된 요구사항을 말하기 어렵다. 대화하며 자신의 생각을 발견하거나 바꾸기도 한다. AI가 초기에 뜻을 단정하면 정교하게 잘못된 결과를 만들고, 반대로 질문과 설계 승인을 반복하면 구현이 지연된다.

이 스킬은 그 사이에서 필요한 의미를 확보한다. 새 아이디어뿐 아니라 기존 기능의 수정, 글쓰기, 학습, 조사 요청에 적용한다. 프롬프트 자체가 필요한지, 이미 승인된 작업을 위해 요청을 잠시 명확히 하는 중인지도 구분한다.

초기 범위는 한국어 텍스트 대화다. 음성으로 입력되어 텍스트가 된 말은 다룰 수 있지만 음성의 억양·표정·침묵 길이를 관찰한 것처럼 해석하지 않는다. 법률·의료 등 분야 지식의 정확성을 이 스킬이 보장한다고 표현하지 않는다.

## 기존 스킬에서 가져올 점과 수정할 점

[prompt-optimizer 원문](https://github.com/github/awesome-copilot/blob/main/skills/prompt-optimizer/SKILL.md)은 완성된 프롬프트 하나를 제공하고, 실제 입력을 포함하며, 정보가 없으면 받는 AI가 질문하도록 구성한다. 입력과 같은 언어를 쓰는 규칙도 있다. 다만 프롬프트 생성 전에 사용자와 의도를 공동으로 발전시키는 절차는 중심이 아니다.

| 요소 | 이번 설계에서의 처리 |
| --- | --- |
| 복사해서 바로 사용할 프롬프트 | 유지한다. 다른 대화에서도 필요한 맥락을 이해할 수 있게 만든다. |
| 정보가 부족하면 받는 AI가 질문 | 먼저 현재 대화에서 중요한 뜻을 정리한다. 사용자가 즉시 프롬프트를 원하거나 자료가 나중에 제공될 때만 후속 질문을 지시에 포함한다. |
| 입력과 같은 언어 사용 | 한국어 대화의 지시 대상, 조건, 강도, 정정을 보존하는 규칙을 추가한다. |
| 긍정문 중심 작성 | 행동을 명확하게 쓰되, 사용자가 명시한 금지와 유지 조건도 남긴다. |
| 일률적인 깊은 사고 문구 | 필수로 붙이지 않는다. 필요한 경우 관찰 가능한 완료 기준을 확인하도록 쓴다. |
| 최종 프롬프트만 출력 | 프롬프트 생성 전에는 필요한 대화를 허용한다. 최종 결과의 설명은 중요한 해석이나 가정을 알릴 때만 짧게 제공한다. |

원본을 직접 번역하거나 덮어쓰기보다는 조사에 근거해 독립된 스킬로 작성하는 안을 권한다. 원문을 재사용하게 되면 구현 단계에서 해당 저장소의 라이선스와 표시 의무를 확인한다.

## 스킬이 작동할 상황

명시적으로 스킬을 부르거나, “내 생각을 프롬프트로 정리해 줘”, “AI에게 어떻게 요청하면 될지 같이 정리하자”처럼 요청 작성의 의도가 분명할 때 적용한다.

기존 기능 수정에서도 프롬프트를 정리해 달라는 요청이면 적용한다. 일반적인 수정 지시를 모두 가로채 별도 프롬프트로 바꾸는 것은 초기 기본 동작으로 두지 않는다. 모든 코딩 요청에 자동으로 개입하는 방식은 사용자가 나중에 원할 때 별도 운영 규칙으로 설계한다.

스킬을 사용하는 대화에서는 완성된 프롬프트를 보여준 뒤 실행 승인을 받는다. “프롬프트 확인 없이 실행”을 명시했다면 그 범위에서 확인을 생략한다. 이미 승인한 같은 프롬프트의 실행에는 승인을 반복하지 않는다.

## 대화에서 유지할 정보

고정된 설문을 사용자에게 보여주기보다, 다음 정보 중 현재 작업에 필요한 것만 관리한다.

| 정보 | 의미 | 기록 예 |
| --- | --- | --- |
| 목표 | 사용자가 얻으려는 결과 | 많은 검색 결과에서 원하는 항목을 쉽게 찾기 |
| 맥락 | 대상, 현재 상태, 사용 상황 | 기존 웹 서비스의 검색 결과 화면 |
| 원하는 변화 | 현재와 달라져야 하는 동작 | 일치하는 검색어가 눈에 띄도록 표시 |
| 품질 기준 | 사용자가 만족을 판단할 조건 | 어떤 부분이 일치했는지 목록에서 확인 가능 |
| 제약 | 유지·금지·우선순위·범위 | 검색 로직과 정렬 순서는 유지 |
| 근거 상태 | 사용자가 말함, 자료로 확인, AI의 제안, 아직 미정 | 강조 표시는 사용자 선택, 색상은 실행자가 결정 |
| 이번 단계 | 탐색, 프롬프트 작성, 실행까지 요청 | 프롬프트 작성만 요청 |

이 표는 설계 설명을 위한 것이다. 실제 대화마다 모든 칸을 채우거나 표를 출력하지 않는다. 사고 과정을 공개하도록 요구하지 않고, 사용자가 확인할 필요가 있는 해석·가정·제안만 말한다.

사용자의 조건, AI가 제안한 선택지, 사용자가 채택한 선택지를 구분한다. AI의 예시가 사용자의 요구사항으로 바뀌는 일을 막는 것이 목적이다.

## 질문을 할지 판단하는 기준

1. 앞선 대화나 접근 가능한 자료에 답이 있는지 먼저 확인한다.
2. 가능한 해석들이 실제 결과의 범위·동작·대상·품질을 다르게 만드는지 본다.
3. 달라진다면 그 차이를 가장 잘 드러내는 질문을 한다.
4. 결과를 바꾸지 않는 빈칸은 구현상의 재량으로 남기거나 작은 가정을 알리고 진행한다.

예를 들어 “좀 더 깔끔하게”는 글에서는 중복 제거일 수 있고, 화면에서는 정보 밀도나 정렬 문제일 수 있다. 앞선 대화가 중복 문장에 관한 것이었다면 그 대상을 다시 묻지 않는다. 화면에서 무엇이 불편한지 드러나지 않았다면 구체적인 장면을 묻는다.

질문의 개수는 법칙처럼 고정하지 않는다. 초기 동작은 중요한 질문 하나를 우선하고, 서로 연결된 짧은 질문은 묶을 수 있게 한다. 두 차례를 넘겨도 의도가 정리되지 않는 경우 같은 질문을 반복하기보다 짧은 후보 문장이나 대비 예시를 보여주는 방식을 시험한다. 이 기준은 연구에서 입증된 최적 횟수가 아니라 대화 부담을 줄이기 위한 시작점이다.

질문 종료 조건은 사용자 목표, 결과를 바꿀 조건, 중요한 제약을 표현할 수 있고 서로 충돌하지 않는 상태다. 아직 정하지 않아도 되는 구현 세부사항까지 확정하지 않는다.

## 한국어로 질문하는 방식

기본 말투는 짧고 자연스러운 해요체를 제안한다. 사용자가 선호를 밝히면 맞춘다. 대화의 말투와 생성할 결과물의 말투는 별도로 다룬다. 사용자가 반말로 말해도 고객 안내문까지 반말로 만들지는 않는다.

질문은 사용자가 이미 말한 목적에 연결한다. 전문 용어로 재질문하기보다 불편한 장면, 바라는 변화, 좋은 예와 싫은 예를 묻는다.

| 원래 요청 | 유용한 질문 예 | 피할 방식 |
| --- | --- | --- |
| 검색을 좀 편하게 해 줘 | 검색어를 넣는 과정과 결과에서 원하는 항목을 찾는 과정 중 어디가 더 불편한가요? 다른 부분이어도 괜찮아요. | 대상 사용자·기술 스택·KPI·일정 전체를 한꺼번에 질문 |
| 글을 덜 딱딱하게 바꾸고 싶어 | 지금 글에서 특히 어색하게 느껴지는 문장 하나를 짚어 주실 수 있어요? | 무조건 반말이나 유행어로 변경 |
| 이 기능 괜찮은 것 같기도 한데 | 도입할지 판단하는 데 도움이 필요한가요, 아니면 넣기로 하고 요청을 정리하려는 건가요? | 곧바로 구현 지시로 확정 |
| 보고서를 제대로 만들고 싶어 | 이 보고서를 읽은 사람이 무엇을 이해하거나 결정하면 좋겠어요? | “제대로”를 AI가 정한 분량·도표 수로 치환 |

위 질문도 문맥에서 이미 답이 확인되면 생략한다. 선택지는 사용자의 표현을 돕기 위한 예시이며, 제시된 범위 안에서만 고르게 하지 않는다.

## 생각을 발전시키되 의도를 대신 결정하지 않는 방법

단순히 빠진 정보를 수집하는 것만으로는 생각이 발전하지 않는다. 사용자가 표현하기 어려워할 때 AI는 다른 관점이나 후보를 제안할 수 있다.

예를 들어 “화면이 복잡해”라는 말에 “정보를 줄이는 방법도 있고, 같은 정보를 더 잘 묶는 방법도 있어요”라고 차이를 보여준다. 사용자가 선택하거나 수정하기 전에는 어느 쪽도 필수 요구사항에 넣지 않는다.

짧은 시안이나 예문은 취향을 표현하기 위한 대화 자료다. 스킬이 프롬프트 작성만 요청받은 상황에서 실제 파일을 수정하거나 제품을 구현하는 근거가 되지는 않는다. 제시된 프롬프트의 실행을 승인받은 상황에서는 작은 결과를 보며 조정하는 방식을 사용할 수 있다.

사용자가 뒤늦게 “아니, 속도보다 결과가 너무 많아서 문제야”라고 하면 속도 개선이라는 가설을 버리고 결과 탐색 문제를 중심으로 정리한다. 초기 해석을 지키기 위해 사용자의 수정을 무시하지 않는다.

## 프롬프트로 변환할 때 보존할 의미

| 언어 현상 | 보존할 내용 |
| --- | --- |
| 이거·그 부분·아까 것 | 문맥에서 확인한 구체적인 대상 |
| 만·도·우선·일단 | 배제, 추가, 우선순위, 현재 범위의 차이 |
| 가능하면·반드시 | 선호와 필수 조건의 강도 |
| 아직·먼저·이후 | 현재 단계와 실행 순서 |
| 하지 말고·그대로 두고 | 변경 금지와 유지 조건 |
| 좋겠어요·해 주실래요 | 문맥에 따른 요청의 기능과 공손함 |
| 같은데·싶어·어떨까 | 탐색, 제안, 요청 중 문맥에서 확인된 의미 |
| 아니·정확히는·그게 아니라 | 앞선 해석을 수정하는 내용 |
| 네·넵·괜찮아요 | 무엇에 대한 응답인지 확인된 범위 |

위 표현을 키워드 규칙으로 분류하지 않는다. 같은 문장도 앞선 질문과 전체 요청에 따라 기능이 달라질 수 있다.

불명확한 평가어를 AI가 임의의 수치로 바꾸지 않는다. “빠르게”가 입력 지연인지 검색 응답 시간인지 확인하지 않은 채 “100ms 이내”를 추가하는 것은 명확화가 아니다. 수치 기준이 필요하면 사용자 요구나 실제 측정 근거를 확보한다.

## 결과물의 형식

OpenAI 공식 가이드의 배경·지시·추가 정보와 제약 구조를 기본으로 하고, 필요한 결과물 형식과 완료 기준을 명시한다. 아주 단순한 요청은 짧게 조정한다. 역할 부여, XML, 장문의 검증 지시를 매번 강제하지 않는다. 다음 내용을 작업에 맞춰 포함한다.

- 수행할 작업과 기대 결과
- 작업에 필요한 맥락과 실제 입력 또는 접근 가능한 자료
- 지켜야 할 조건과 이번 범위
- 관찰 가능한 완료 기준
- 자료가 아직 없는 경우 자료를 받거나 먼저 확인할 방법

프롬프트는 하나의 코드 블록으로 제공하는 것을 기본으로 한다. 중요한 가정을 알려야 할 때만 앞에 한두 문장을 붙인다. 확정하지 않은 핵심 정보를 빈칸으로 숨긴 채 완성됐다고 말하지 않는다.

다른 AI에 전달할 프롬프트에는 “아까 말한 대로” 같은 이 대화 전용 참조를 남기지 않는다. 파일이나 이미지는 실제 제공 여부를 적고, 새 대화에서 접근할 수 없는 로컬 경로를 접근 가능한 자료인 것처럼 다루지 않는다. 긴 원문이 필요하면 별도 첨부와 입력 절차를 명시한다.

다음은 실제 사용자 데이터나 실험 결과가 아닌 설계 예시다. 같은 프로젝트를 열어 둔 코딩 AI에 전달하는 상황을 가정한다.

**사용자:** 검색 좀 편하게 바꾸고 싶어. 지금 찾기 힘들어.

**AI:** 검색어를 입력하는 과정이 불편한가요, 아니면 결과에서 원하는 항목을 찾기가 어려운가요?

**사용자:** 결과가 많으면 뭐가 검색어랑 맞는 건지 모르겠어. 순서는 그대로 두고 일치하는 부분만 눈에 띄면 좋겠어.

이 답으로 대상과 원하는 변화, 유지 조건이 드러난다. 색상이나 구현 라이브러리까지 질문할 필요는 없다. 생성할 프롬프트의 예는 다음과 같다.

```text
현재 프로젝트의 검색 결과 목록에서 검색어와 일치하는 부분을 알아보기 쉽게 표시해 주세요. 사용자가 많은 결과 중 어떤 부분이 검색어와 맞는지 빠르게 파악하는 것이 목적입니다.

먼저 현재 검색 방식과 결과 목록 구현을 확인하세요. 검색 로직, 결과 순서, 검색어 입력 방식은 유지하고 결과 표시를 수정하세요. 강조 표현은 기존 디자인에 맞춰 정하세요.

완료 기준은 검색어와 일치하는 부분을 결과 목록에서 구분할 수 있고, 기존 검색 결과와 정렬이 유지되는 것입니다. 일치 기준은 현재 검색 동작을 따르세요. 구현을 확인해도 강조 대상이 달라질 중요한 모호함이 남을 때만 질문하세요.
```

이 예시에서 “기존 디자인에 맞춤”은 구현 재량에 관한 제안이다. 사용자에게 별도 색상이나 라이브러리를 요구한 것으로 표현하지 않는다. 실제 프롬프트를 생성할 때에는 대화의 허용 범위와 프로젝트 맥락에 맞춘다.

## 실행으로 넘기는 경계

프롬프트 작성만 요청받으면 프롬프트를 제공하고 종료한다. 기본 실행 흐름은 프롬프트 제시 → “이 프롬프트로 작업을 진행해도 될까요?” → 사용자 승인 → 실행이다. 일반적인 작업 요청만으로 프롬프트 확인 단계를 생략하지 않는다. 수정 요청이면 갱신한 프롬프트를 다시 확인받는다.

명확한 요청에는 명확화 질문 없이 바로 프롬프트를 작성하되 실행 승인 질문은 남긴다. 이 승인 흐름은 2026년 10월 9일 실제 사용 피드백으로 수정한 요구사항이다. 연구·설계·명세에 대한 별도의 반복 승인 절차를 추가하지 않는다.

## 검증 계획

기본 동작은 [검증 기록](skill-validation.md)의 사례로 점검했다. 성능 우위는 아직 검증하지 않았다. 아래 비교를 통해 스킬이 기존 모델의 능력에 실제로 도움이 되는지 확인할 수 있다.

### 비교할 조건

같은 모델, 같은 원문과 대화 맥락, 같은 도구 접근 조건으로 세 가지를 비교한다.

1. 기본 모델에 프롬프트 작성을 직접 요청
2. 기존 prompt-optimizer 적용
3. 제안 스킬 적용

비교는 두 부분으로 나눈다. 먼저 동일한 완성 정보로 프롬프트 변환 자체를 비교한다. 그다음 모호한 입력부터 시작해 대화까지 포함한 전체 흐름을 비교한다. 두 번째 비교에서는 질문 수, 소요 시간, 사용자가 새로 제공한 정보도 기록한다. 질문 비용은 프롬프트 생성 단계뿐 아니라 받는 AI의 후속 질문과 최종 결과까지의 재작업도 포함한다. 새 스킬에만 추가 정보를 주고 프롬프트 품질이 좋아졌다고 결론 내리지 않는다.

### 초기 사례 구성

아래 10개 유형에 각각 3개씩, 총 30개 사례로 시작하는 안이다. 20개는 개발 중 점검, 10개는 수정에 사용하지 않는 보류 사례로 둔다. 유형이 양쪽에 들어가게 나누고, 단순한 표현 바꿔 쓰기만을 별도 사례로 세지 않는다.

| 유형 | 살필 실패 |
| --- | --- |
| 이미 명확한 수정 | 불필요한 질문과 계획 생성 |
| 생략·지시어 | 대화에 있는 대상을 다시 묻거나 다른 대상을 선택 |
| 만·도·우선 | 배제·추가·우선순위를 혼동 |
| 금지·조건·시점 | 유지 조건 누락과 실행 순서 변경 |
| 공손한 명확한 요청 | 공손함을 망설임으로 오해 |
| 탐색·맞장구 | 의견 탐색이나 수신 확인을 실행 지시로 확대 |
| 발화 정정 | 폐기된 요구를 최종 프롬프트에 남김 |
| 추상적인 품질 요구 | 분량·수치·기능을 임의로 추가 |
| 도메인과 문체 전환 | 사용자 말투를 결과물 대상에게 부적절하게 적용 |
| 다른 대화로 전달 | 누락된 맥락, 접근 불가능한 자료, 불필요한 재질문 |

같은 의미를 반말·해요체·하십시오체로 바꾼 대응 사례와, 같은 표면 문장에 서로 다른 앞선 대화를 붙인 대응 사례도 포함한다. 이는 정중한 표현에 대한 선호와 의도 해석 능력을 구분하기 위한 장치다.

### 평가할 결과

| 지표 | 판정 방법 |
| --- | --- |
| 의도 보존 | 사용자가 확인한 목표와 핵심 조건이 남아 있는지 검토 |
| 조건 손실 | 명시된 유지·금지·범위 조건 중 빠진 항목 수 |
| 요구 날조 | AI 제안을 사용자의 확정 요구로 바꾼 항목 수 |
| 질문의 효용 | 답변이 목표·범위·품질 기준 중 하나를 실제로 해소했는지 판단 |
| 대화 부담 | 생성·수신 단계 전체의 질문 횟수, 사용자 응답 시간, 같은 질문 반복, 재작업, 체감 부담 |
| 실행 가능성 | 별도 실행자가 핵심 의도를 불필요하게 다시 묻는지 확인. 미리 예정한 자료 수집은 의도 재확인과 구분 |
| 최종 결과 적합성 | 실제 결과물이 사용자 기준에 얼마나 맞는지 이름을 가린 비교 |
| 한국어 자연스러움 | 원어민 평가자가 문맥에 맞는 질문과 말투인지 판단 |

가능하면 사용자와 독립적인 한국어 평가자 한 명이 각각 평가하고, 불일치 사례를 검토한다. 모델이 만든 정답 의도를 또 다른 모델이 채점한 결과만으로 성공을 주장하지 않는다. 같은 프롬프트도 결과가 달라질 수 있으므로 차이가 불안정한 사례는 반복 실행해 확인하고 모델 버전과 날짜를 기록한다.

보류 사례에서 중요한 금지·유지 조건 손실과 탐색 대화의 무단 실행 전환이 없어야 한다는 것을 초기 필수 기준으로 제안한다. 이는 전체 성능 100%를 보장한다는 뜻이 아니다. 질문은 적을수록 무조건 좋은 것이 아니라, 필요한 질문으로 결과가 좋아진 정도와 함께 판단한다.

한국어 보완 규칙의 효과를 주장하려면, 대화 명확화만 적용한 버전과 한국어 의미 보존 규칙까지 적용한 버전도 비교한다. 전체 스킬이 좋아졌다는 결과만으로 한국어 규칙이 원인이라고 결론 내리지 않는다.

## 구현 이후 확인할 내용

핵심 규칙과 참고 예시 작성, 공식 구조 검증, 12개 대화 사례와 파일 수정 1건 점검, 예시의 모호함 수정, 사용자 전역 설치를 완료했다. 실제 사용에서 불필요한 질문과 의도 손실을 관찰하고, 효과를 비교하려면 위의 전체 평가 계획을 별도로 수행한다.

이 조사에서 바로 채택할 수 있는 원칙은 맥락 활용, 의미와 제약 보존, 높임과 요청 강도의 구분이다. 질문 방식과 횟수, 출력 길이, 자동 개입 범위는 사용성 평가를 통해 정할 항목으로 남긴다.
